# 历史第一阶段：摄像头选型验证方案

## 目的与执行边界

本文保留当时使用UGREEN USB摄像头形成购买依据的实验口径和结果表模板。选型阶段已经结束，正式摄像头已更换为固定在灯头上的IMX179；当前正式设计和开发要求见[视觉功能设计与开发准则](VISION_DESIGN.md)，当前交付顺序见[开发路线](ROADMAP.md)。

本文不是当前正式实现方案。历史实验使用独立测试程序，不接入正式app、不触发视觉动作控制；表格中的空白模板不表示没有完成后续实测。

## 1. 实验前记录与设备检查

1. 记录 Pi5 系统、内存、Python/ARM64 环境、散热、电源、已有运行进程及软件版本。核对候选 MediaPipe、OpenCV 与现有 NumPy 的兼容性；未来实验优先使用独立环境，不直接调整正式运行环境。
2. 记录 UGREEN 的具体型号、设备标识、接口、尺寸、重量、线材走向和可能的安装限制；未知项标记待确认，不按品牌推断规格。
3. 枚举设备真实支持的分辨率、帧率、像素格式组合，记录 MJPEG/YUYV 等实际可用格式。不能将设置参数成功或接口读回值视为实际帧率证明。
4. 在实际桌面位置测量近、常用、远三个距离并记录厘米值，检查水平/垂直覆盖、脸与手能否同时入镜。记录对焦方式、最近可用距离、曝光变化、逆光表现及运动模糊。
5. 将摄像头能力、镜头/安装限制、算法限制和主机计算限制分开记录。当前临时摆放不能证明最终安装效果。

## 2. 测试矩阵与顺序

| 维度 | 基础组合与扩展条件 |
|---|---|
| 摄像头输出 | 320×240、640×480；细节不足时再加设备支持的更高分辨率 |
| 申请帧率 | 10 / 15 / 30 FPS，仅测试设备支持的组合；不支持的标记跳过及原因 |
| 像素格式 | 记录每组实际格式；支持多格式时先在常用组合比较解码成本、帧率和延迟 |
| 模型输入 | 独立记录模型输入尺寸、缩放/裁剪方式，不能与摄像头输出尺寸混为一谈 |
| 工作负载 | 仅采集；YuNet；MediaPipe；YuNet + MediaPipe；组合负载中按需 SFace |
| 场景 | 无人无手、单脸、单手、双手、人脸加手、偶尔多人；覆盖距离与光照 |

执行顺序：

1. **采集基线：**先遍历受支持的基础组合，排除不稳定、严重积压或无法成像的设置。
2. **单项测试：**分别跑 YuNet 与 MediaPipe，使用相同场景比较成本和稳定性。MediaPipe 用 `VIDEO` 或 `LIVE_STREAM` 模式，记录手数量上限；单手与双手分别测试。
3. **组合测试：**对单项表现可用的组合运行人脸加手；单一摄像头采集源提供最新帧，不重复打开设备，不累计无界队列。
4. **身份成本：**使用清晰人脸验证 YuNet 五点对齐到 SFace 的流程，分别测首次加载、模型驻留内存及单次调用；再测组合运行时的按需调用峰值。本阶段不建设主人数据库或正式身份功能。
5. **语音共存：**依照第 5 节与正式语音基线对比，选出适合持续运行的候选配置。
6. **选型分析：**以识别失败和资源瓶颈决定是否需提高分辨率、改善镜头/曝光、降低推理频率或进一步考察加速硬件。

默认每组预热 30 秒、测量 2 分钟、重复 3 次；最终候选进行至少 15 分钟持续负载观察。记录实际时长与中断原因，缺测不可填为零。该默认用于可比性，并非声称这些时长足以覆盖所有长期问题。

## 3. 场景与识别效果

- 在已记录的近、常用、远位置分别采样，记录脸框/手框像素宽高及是否被画面边缘裁切。
- 覆盖正面、侧脸、短暂遮挡，单手/双手、人脸和手同时存在；用多人场景观察检测稳定性，不在本阶段实现目标选择。
- 覆盖常用照明、暗光和逆光；每个场景记录光源方向与曝光/对焦设置，能锁定设置时记录是否锁定。
- 静态手势使用 `Open_Palm`、`Closed_Fist`、`Thumb_Up`、`Thumb_Down`、`Victory`、`Pointing_Up` 等候选类别；每类每个重点场景重复展示 10 次，每次保持约 2 秒并移出画面再开始下一次。记录检测到的展示次数、分类正确次数、输出抖动和首次正确结果等待时间。
- 增加无人无手、自然打字、拿杯子等非命令场景，记录错误类别出现及连续误识别时长。逐帧类别误识别不等于未来命令误触发，报告中不得混用。
- 保留失败场景说明；确需保存图片或短片时只使用知情参与者，记录位置和采集条件，原始影像不提交 Git。默认不连续保存完整摄像头视频。

## 4. 指标及统计口径

| 指标 | 记录方法与限制 |
|---|---|
| 实际采集 FPS | 单调时钟测量窗口内成功取得的帧数；注明后端时间戳和重复帧检查能力，不能仅抄申请值 |
| 实际推理 FPS | 分别统计 Face/Hand 完成结果数；异步调用另记提交数、完成数和丢弃数，不能用提交速率代替完成速率 |
| 推理延迟 | 单项处理开始到结果完成，分别报告 P50/P95；冷启动/模型加载单列 |
| 软件端到端延迟 | 采集时间戳到结果可用的 P50/P95，并注明时间戳是在驱动还是应用读取时生成 |
| 摄像头读取 | 记录读取调用耗时与缓冲情况；读取快不等于画面新，不能据此推断真实拍摄延迟 |
| 帧积压 | 记录结果对应帧的年龄、丢帧及队列策略；仅保留最新帧，区分主动丢旧帧与设备故障 |
| CPU | 记录进程与全系统平均/峰值、采样间隔及百分比口径（单核或全机归一化），固定记录推理线程配置 |
| 内存 | 进程峰值 RSS、整机可用内存、swap 使用与换入换出变化；单独标注 SFace 驻留和调用峰值 |
| 热稳定性 | 记录开始/结束/峰值温度、频率和降频状态，结合持续负载判断 |
| 识别质量 | 按场景给出展示次数、有效检测/正确分类次数、漏检、误识别、抖动及失败原因 |

软件时间戳一般不能直接代表传感器曝光时刻。没有硬件时间戳或独立测量时，端到端指标必须标为软件链路延迟；传感器曝光、USB 缓冲等未知部分另列，不能宣称测出了完整物理延迟。

## 5. 与现有语音并行验证

先检查现有 app 和 Pi Agent 状态，复用单一正式实例。视觉程序只占用摄像头；不启动第二份 app、声卡诊断或串口程序，不改语音参数。

先关闭视觉建立语音基线，再以同样条件运行人脸加手，最后增加按需身份推理。采用相同语句和播报素材，每种条件至少重复 10 次唤醒、短问答和静止时自然插话，记录样本数、成功次数及失败说明；记录明确停止词表现。已有语音任务本身若带运动，沿用现有仲裁，不由视觉发起动作。

比较唤醒漏检、TTS 首音/回答响应延迟、自然插话检出与误打断、音频卡顿、HTTP/Agent 响应及整机资源变化。能从现有日志得到的指标标注时间边界；不能测得的标为未测，不能用主观感受填数值。现有语音已存在的失败与新增退化分开报告。

这一阶段只验证计算负载共存，**不代表已验证 tracking 的运动噪声或 Barge-in 状态兼容性**；这些属于新摄像头安装后的正式集成验收。

## 6. 评价与购买需求交付

手势约 15 FPS、人脸约 8～15 FPS 是待验证目标，不是未经测量的性能承诺。结合延迟、效果、内存余量和语音变化评估，不能只凭平均 FPS 宣布通过；出现持续积压、内存压力、明显降频或语音退化的配置不列为推荐配置。

报告需区分：

- **最低可接受参数：**哪些输出组合、视场、近距成像与接口能力有实验支持，适用的距离和光照范围是什么。
- **推荐参数：**相对最低需求保留何种余量，以及帧率、清晰度、功耗、体积和成本的取舍依据。
- **必需与可选特性：**例如能同时容纳脸和手的视场、合适的最近对焦距离、可安装尺寸；自动对焦或更高帧率是否必要必须有场景证据。
- **瓶颈与未知：**区分视场/成像、传输/解码、模型计算和资源竞争；不能把提高相机输出帧率当成提高推理 FPS 的保证。
- **加速硬件：**仅在有计算瓶颈证据时进一步评估，逐项核对候选模型能否部署、支持的算子/转换方式、输出是否包含所需关键点、数据传输和主机预后处理成本。带 AI 标签不代表自动加速当前候选模型。
- **安装复验：**现有摄像头和临时摆放不能保证新摄像头表现；列出到货后必须复查的方向、视角、曝光/对焦、模糊、线材活动空间和驱动兼容性。

缺乏证据的参数明确标为待验证。即使候选都未达到目标，也应形成失败原因与下一步测量建议，不虚构推荐规格。
