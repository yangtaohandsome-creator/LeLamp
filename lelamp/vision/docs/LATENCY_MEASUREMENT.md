# 视觉分段延迟实测（2026-09-28）

## 复现与边界

在 Pi5 项目根目录运行（先停止其他摄像头/运动占用者）：

```bash
DISPLAY=:0 .venv/bin/python -u scripts/vision_latency.py --seconds 90
.venv/bin/python scripts/analyze_vision_latency.py runtime_state/tracking_diagnostics/latency-1790575252893824479.jsonl
```

脚本复用正式全屏 follow 预览、原有控制参数和睡眠退出流程；限定时间结束后停止，不留下后台跟随。按帧序号关联采集/感知/显示，按完全一致的 captured_at 关联控制目标，区分首次消费和重复消费。不推测未匹配目标对应的帧。使用有界异步写盘，默认普通运行不开启记录。显示子进程通过有界队列回传时间戳。

本次记录90秒，剔除前10秒；673个感知结果、1939个控制周期、1902个有效目标写入关联，2个无法关联的边界目标排除；记录丢失0，写入错误无。469帧检测到手（含20帧双手），204帧无手；机械源全程face，因此已覆盖手部算法耗时，但**没有实测手部作为运动源时的完整消费延迟**。场景不是严格同轨迹基准。

采集实测21.65FPS，感知8.69Hz；V4L2查询仍为30FPS，不能把请求值当实际值。测试中两次温度采样85.35°C、84.25°C，throttled分别0xe0006、0xe0008，后一次ARM时钟约1.5GHz。这是当前热状态下的实测，不代表充分散热后的上限，尚未做散热前后A/B或记录开关严格A/B。

采集read等待+解码P50=35.34ms/P95=64.4ms；旋转发布0.68/1.18ms。read包括等待新帧，不能解释为MJPEG解码的CPU开销，也不能当作曝光到主机耗时。显示额外耗时主要在放大全屏/imshow/waitKey（23.64/28.47ms），进程传输4.34/7.64ms、绘制1.26/1.91ms、父进程轮询5.65/10.35ms。

captured_at在OpenCV read返回后记录，未包含曝光/USB/驱动缓存之前的时间。显示提交不是屏幕发光，串口写完不是机械实际到位；这些需要外部高速摄影或设备时间戳进一步验证。官方MediaPipe整图内部的掌检测、关键点、原始分类尚未拆分，不能把99ms都归因于分类头。感知被采样和结果复用也会增加用户动作到下一次有效响应的等待，首次消费延迟不等于完整动作响应时间。

## 判断及优化优先级

1. 先恢复稳定散热并用同脚本复测。当前热限频是明确干扰因素；不能用这次数据承诺改善百分比。
2. MediaPipe官方链约99ms，是主要计算耗时。补充两条分类合计约1.4ms（有手样本均值），移除融合不能解决主要延迟。进一步检查原始图内部重检测、线程和推理路径，再比较结果质量/耗时；不直接降低手势可靠性。
3. 当前YuNet完成后要等待手链，统一发布。后续可将脸和手结果独立及时发布，保留各自帧号、时间戳、仲裁和过期检查；这有望减少人脸等待手链的时间，但对跟手不能省掉手部推理。不要未经测量就开双推理线程，Pi5的CPU争用可能更差。
4. 实采21.65FPS而设置30FPS，采集返回到取帧P95达53ms。先在恢复散热后确认采集率，再排查自动曝光/驱动/调度；本机V4L2未暴露曝光控制。本次不能证明是曝光或缓存导致。
5. 显示额外约35ms可从全屏缩放、GUI提交和轮询优化，但它不是主控制延迟。当前控制40ms间隔P95=41.46ms，显示隔离仍有效。改成最新原始画面预览必须注明检测框属于旧帧，否则会产生框画面错位。
6. 暂不继续加运动增益。当前目标年龄约194ms（P95=276ms）意味着控制常用旧观测，是高增益回摆的合理诱因，但本次没有证明它是唯一原因。保留当前速度上限和制动参数，先降低感知延迟再复测快速移停。

本次仅增加可选测量与分析，没有调整速度、加速度、增益、阈值、采集配置或分类逻辑。本地157项测试通过。结束时已停止测试预览并睡眠释放扭矩。
